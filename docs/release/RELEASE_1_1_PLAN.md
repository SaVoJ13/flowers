## 1. Продуктова модель, на якій стоїть план (ADR-015)

1. **Картки догляду безкоштовні для всіх.** Основа: вбудований **каталог перевірених карток** (офлайн): ціль 150–200 кімнатних рослин × 4 мови (uk, en, ru, pl).
2. **ШІ-генерація картки** для рослини, якої немає в каталозі, лишається безкоштовною (Gemini на безкоштовному рівні через Firebase AI Logic). Згенерована картка зберігається **лише локально**; **спільного кешу ШІ-карток немає**. Картка генерується мовою інтерфейсу.
3. **Сигнал попиту:** коли пошук нічого не знайшов у каталозі, застосунок анонімно записує у Firestore (лише create) нормалізовану назву + мову + дату. За цим списком додаються картки наступними оновленнями.
4. **Платне (пізніше, Blaze, відкладено):** ШІ-діагностика за фото, персональні поради для конкретної рослини з урахуванням умов, чат.

## 4. Формат каталогу, міграції й оновлення без втрати даних

### 4.1. Проблеми поточного стану (за аналізом коду, `file:line` у картках завдань)
- JSON каталогу: плоский масив 20 рослин, лише `name_uk`; `difficulty`, `light`, `soil_type` це **вільний український текст**, не ключі (`CatalogScreen.kt` виводить їх як є); словник difficulty у JSON і в ШІ-промпті різний.
- Каталог завантажується лише при **порожній таблиці** (`count()==0`, `FlowersDatabase.kt`, `FlowersRepositoryImpl.kt`): новий каталог не дійде до існуючих користувачів. Версії контенту й джерел у записах немає.
- Room v2 (`exportSchema=true`, схема лише `2.json`; `1.json` нема), явна міграція 1→2 є, `fallbackToDestructiveMigration` не використовується (добре).
- `plants.speciesId` без FOREIGN KEY: якщо змінити/видалити id виду, посилання «висне» без помилки.
- Поди видів прив'язані до 8 видів із 20 (14 подів), ще 4 загальні (`general_beginner`), тексти в колонках `*Uk`; дерево симптомів `*_uk`.

### 4.2. Принципи
1. **ID рослини стабільний назавжди.** **20 наявних ID (`monstera`, `calathea`, `ficus_benjamina` … повний перелік у `PLANT_CATALOG.json`) зберігаються без змін**; латинський slug-формат діє лише для нових рослин (B0 переписує тексти, а не ID); валідатор перевіряє, що всі ID з v2 присутні. Не перевикористовується, не видаляється; застарілу картку позначаємо `retired` (з `replacedBy`). Тоді `plants.speciesId` ніколи не висить.
2. **Мовонезалежні факти окремо від текстів.** Рівні складності, світла, токсичність: переліки (enum), що перекладаються через `strings.xml`. Тексти: по мовах.
3. **Імпорт ідемпотентний і версійний:** перевіряється `contentVersion`, а не порожність таблиці. Імпорт торкається лише записів `origin=BUILTIN`; ШІ-картки (`origin=AI`) і «Мої рослини» не змінюються ніколи.
4. **Кожен факт має джерело** в даних; безпека для тварин/дітей без джерела = `UNKNOWN`.
5. **Нічого з мережі:** каталог лише з assets (офлайн). Нові рослини приїжджають з оновленням застосунку.

### 4.3. Формат файлів у репозиторії (джерело істини, `app/src/main/assets/catalog/`, дублюється в `docs/content/catalog/`)
```
catalog/
  manifest.json        { "contentVersion": 7, "schema": 1, "batches": ["b00","b01", ...] }
  sources.json         { "<sourceId>": { "title", "publisher", "url", "kind": "extension|botanical|society|other" } }
  b00.json … b07.json  масив карток (≈25 шт.), одна партія = один файл
```
Картка (чернетка схеми, `schema: 1`):
```json
{
  "id": "monstera_deliciosa",            // для НОВИХ рослин: латинський slug; наявні 20 ID лишаються (напр. "monstera")
  "latin": "Monstera deliciosa",
  "family": "Araceae",
  "retired": false, "replacedBy": null,
  "care": {
    "difficulty": "EASY",                 // VERY_EASY|EASY|MEDIUM|DEMANDING

    "children": "UNKNOWN",
    "sourceIds": ["mbg_monstera"],        // обов'язково, якщо не UNKNOWN
    "aspcaUrl": "https://www.aspca.org/..."   // лише посилання, даних не копіюємо
  },
  "i18n": {
    "uk": { "name": "Монстера делікатесна", "aliases": ["монстера","швейцарський сир"],
```

### 4.4. Схема Room v3 (міграція 2→3, **без DROP/DELETE**)
- `catalog_plants` (існує): лишаємо старі колонки (`nameUk` тощо) без видалення (SQLite DROP COLUMN на minSdk 26 не гарантовано); додаємо: `origin` (`BUILTIN|AI`), `family`, `difficultyKey`, `lightMin`, `lightMax`, `humidityKey`, `soilKey`, `petsSafety`, `childrenSafety`, `retired`, `replacedBy`, `contentVersion`. Існуючі рядки: `isAiGenerated=1` → `origin=AI`, інакше `BUILTIN`.
- Нова `catalog_plant_i18n` (PK `plantId, lang`): `name`, `aliases` (текст, розділений `|`), `summary`, `watering`, `light`, `soil`, `tip`. Міграція переносить наявні `nameUk/popularName/light/soilType` у рядки `lang='uk'` (дані користувача зберігаються; ШІ-картки лишаються з однією мовою, показ з відкатом на наявну мову).
- Нова `catalog_sources` (`plantId, sourceId, kind`) + `catalog_source_defs` (`sourceId, title, url`).
- Нова `content_meta` (`key, value`): `catalogContentVersion`, `importedBatches`.
- `plants`: без змін (`speciesId` лишається). Додатково тест «усі `speciesId` існуючих рослин резолвляться після імпорту».
- Експорт схеми v3 (`3.json`) і **тест міграції 2→3** (JVM, sqlite-jdbc, як `MigrationTest`; мутаційна перевірка як у QA сесії 015). Окремо: тест на копії даних Власника на телефоні.

### 4.5. Імпорт і майбутні оновлення
- `CatalogImporter` у **транзакції**: читає `manifest.json`; для кожної партії, версія якої вища за збережену, робить upsert за `id` лише серед `origin=BUILTIN`; тексти (`i18n`) замінює повністю для цього `id`; джерела так само.
- Запускається на старті у фоні після відкриття БД і не залежить від `count()==0`. Старий prepopulate (`PrepopulateCallback`, `ensurePopulated`) зводимо до одного шляху (зараз їх два).
- Додавання рослин у наступних релізах: нова партія `bNN.json` + рядок у `manifest.json` + `contentVersion++`. Дані користувача й ШІ-картки не торкаються.
- Правка наявної картки: той самий `id`, вищий `contentVersion` партії. Заміна виду: стара `retired:true, replacedBy:<id>`; у UI рослина користувача показується як є.
- Об'єм: ≈ 200 карток × 4 мови × ≈ 1,2 КБ ≈ 1 МБ (оцінка, перевірити фактом після B0–B2).
- **Поди й дерево симптомів:** поди окремих видів **замінюються текстами картки каталогу** (`watering/soil/tip`), 4 загальні поди (`general_beginner`; усього наразі 18 подів, з них 14 належать 8 видам і замінюються текстами каталогу) і дерево симптомів (11 симптомів) перекладаються на 4 мови (TASK-035) і переходять на мовні файли `assets/content/<lang>/…`. Рекомендація Архітектора; змінює UX подів, тож пропоную Власнику схвалити (питання Q-1.1-7).

## 7. Сигнал попиту (TASK-027-B / TASK-044): проєкт рішення

**Що записується:** лише `normalizedName` (нижній регістр, обрізання, одиночні пробіли, лише літери, пробіл, дефіс і апостроф, 2–60 символів; та сама нормалізація, що в §4.6), `lang` (мова інтерфейсу: `uk|en|ru|pl`), `createdAt` (серверний час, `== request.time`; перевіряється правилами, на відміну від рядка з клієнта; аналізуємо лише дату). Жодних ідентифікаторів користувача чи пристрою, версії застосунку, текстів скарг.

**Коли:** пошук у каталозі нічого не знайшов (не для самої генерації). Клієнтські фільтри: назва проходить шаблон «лише літери, пробіл, дефіс, апостроф; без цифр, `@`, `://`», не більше 4 слів (щоб не потрапляли імена й адреси); не частіше N записів на добу з пристрою; **кожну пару (lang, name) пристрій відправляє один раз** (множина хешів у SharedPreferences, без зміни схеми Room). Перемикач «Допомагати розширювати каталог» у Налаштуваннях (Q-1.1-3). Помилку запису (зокрема `PERMISSION_DENIED`) клієнт **мовчки ігнорує**: без діалогу, без повторів.

**Схема документа (рекомендований варіант A):** колекція `demand`, **автогенерований ID**, поля `normalizedName`, `lang`, `createdAt`. Кожен документ = «один пристрій шукав цю рослину» (з точністю до перевстановлень застосунку). Поки пристрій відправляє пару один раз, кількість документів з однаковим `(lang, normalizedName)` наближає кількість різних пристроїв.

**Чому не шарди (варіант B розглянуто й відхилено за QA PR #11):** шард вибирає клієнт, тож один скрипт створить усі шарди будь-якої назви, а чесні пристрої колідують (при 50 шардах «заповнено» лише приблизно при 200 пристроях); ID з назвою вимагає узгодити slug із `normalizedName` у правилах, що не підтверджено документацією; захисту квоти це не дає (різних назв нескінченно).

**Підрахунок:** Firestore не агрегує без сервера. Перегляд лише Власником: консоль (фільтр за `normalizedName`/`lang`) або локальний скрипт, який Власник запускає зі своїм входом (дані не передаються агентові, агент отримує лише агрегований список «назва → кількість»). Експорт даних без Blaze і сам механізм скрипта НЕ ПІДТВЕРДЖЕНО (перевірити в TASK-027-B). Термін зберігання 12 місяців (пропозиція), видалення вручну (квота видалень 20 тис./добу).

**Чернетка правил (НЕ ПЕРЕВІРЕНА; перевірити в емуляторі до публікації):**
```
match /demand/{docId} {
  allow read, update, delete: if false;
  allow create: if
    request.resource.data.keys().hasOnly(['normalizedName','lang','createdAt']) &&
    request.resource.data.keys().hasAll(['normalizedName','lang','createdAt']) &&
    request.resource.data.normalizedName is string &&
    request.resource.data.normalizedName.size() >= 2 &&
    request.resource.data.normalizedName.size() <= 60 &&
    request.resource.data.normalizedName.matches('^[\\p{L}][\\p{L} \\-\']*$') &&
    request.resource.data.lang in ['uk','en','ru','pl'] &&
    request.resource.data.createdAt == request.time;
}
```
**Перевірити в емуляторі:** чи підтримує `matches` клас `\p{L}` (RE2; якщо ні, явні діапазони літер uk/ru/pl/en); `createdAt == request.time` для `serverTimestamp()`; відхилення: зайве й відсутнє поле, `lang='de'`, довжини 1 і 61, цифри й `@` у назві, `read/list/update/delete`, повторний `set` існуючого документа. Правила **не** перевіряють App Check (підтверджено документацією): склад символів і формат у правилах лише мінімальний захист, клієнтські фільтри можна обійти прямим REST-запитом.

**Захист і спільна квота:** App Check enforcement для Firestore (дія Власника, після моніторингу, як для 027-A). **Квота 20 тис. записів/добу спільна для `reports` і `demand`** (одна безкоштовна база на проєкт): спам у `demand` може заблокувати **скарги**, обов'язкові за політикою Play. Пом'якшення: enforcement App Check, ліміти на пристрій, моніторинг використання в консолі, аварійний вимикач: Власник публікує правило `allow create: if false` для `demand` (скарги лишаються). Фінансового ризику на Spark немає.

**Як використовується:** раз на пару тижнів Власник надсилає топ назв, агент додає їх у список партій (TASK-045).

**Приватність і політика:** розкрити як «анонімна назва рослини, не знайденої в каталозі, мова й серверний час запису; без ідентифікаторів; можна вимкнути в Налаштуваннях». Користувач може ввести й не-рослинний текст (наприклад ім'я); фільтр «до 4 слів, лише літери» зменшує, але не усуває ризик; сказати про це в політиці.
