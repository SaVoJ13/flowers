### [INBOX-011] Щорічне видалення скарг з Firestore (інструкція Власнику)
- **Чому:** TTL-політика недоступна на тарифі Spark (`403: Project flowers-e7b27 has billing disabled`), а політика обіцяє зберігання до 12 місяців.
- **Що робити щонайменше раз на 12 місяців (нагадування в `TASK_BOARD.md`, перше: 2027-11-20):** консоль Firebase → Firestore Database → Data → колекція `reports` → видалити **усі** документи, створені до дати чистки (відкрити колекцію, вибрати всі, Delete; або ⋮ біля колекції → Delete collection). Так жодна скарга не живе довше 12 місяців, як обіцяє політика (не видаляти лише «старші за 12 місяців»: тоді свіжа скарга проживе майже 24). Кількість очікується малою. Якщо перейдете на Blaze: Firestore → TTL → політика на `reports.expireAt` (поле вже записується).
- **Хід:** очікує виконання щороку.

- **Контекст:** На виконання рішення Власника щодо обов'язкового додавання фотографій у персональний чат Flowers 2.0 MVP підготовлено архітектурний проєкт `docs/architecture/PHOTO_ARCHITECTURE_PROPOSAL.md` (PR #42). До затвердження жодного коду не реалізується.
- **Питання 1 (Модель зберігання вкладень):**
  - *Варіант A:* Розширення `ChatMessageEntity` полями `imageUri: String?` тощо. (Простіше зараз, але обмежено 1 фото назавжди, для порівняння фото знадобиться нова міграція).
  - *Варіант B (Рекомендовано):* Окрема таблиця `chat_attachments` із зовнішнім ключем `messageId` на `chat_messages(id)` з `ON DELETE CASCADE`. (Таблиця `chat_messages` не змінюється взагалі, міграція суто адитивна, архітектурно готова до зв'язку 1:N для майбутнього порівняння старих і нових фотографій).
  - *Питання до Власника:* Чи погоджуєте Ви затвердження Варіанту B?
- **Питання 2 (Параметри стиснення та роздільна здатність фото):**
  - *Рекомендація:* Максимальний розмір 1536 px по довшій стороні, якість 85% JPEG (профіль аналогічний фото-діагностиці). Нативне видалення EXIF/GPS, розмір файлу ~200–500 КБ, відмінна деталізація для розпізнавання шкідників і плям без перевантаження оперативної пам'яті.
  - *Питання до Власника:* Чи підходить зазначений баланс якості та оптимізації?
- **Питання 3 (План поетапних PR після PR #42):**
  - *Рекомендація:* Реалізувати функціонал невеликими окремо тестованими PR:
    1. PR #43: Room v5 Schema & Migration (`MIGRATION_4_5`, тести міграції на реальній SQLite);
    2. PR #44: Chat Photo Storage & Lifecycle Service (`ChatPhotoManager`, `ImageProcessor`, очищення сиріт);
    3. PR #45: Gemini Multimodal Service & Repository Contract (мультимодальний виклик `gemini-3.5-flash-lite`, безпечна серіалізація промпту, очищення застарілих параметрів temperature);
    4. PR #46: Multimodal `ChatViewModel` & State (стан вкладення, прев'ю, retry без втрати фото, тести);
    5. PR #47 (STEP 4): UI & Navigation (`PlantChatScreen` у Jetpack Compose, вибір фото, повноекранний перегляд).
  - *Питання до Власника:* Чи затверджуєте Ви запропонований план реалізації?

### Доповнення до [INBOX-015] — умовне погодження Власника (2026-11-28)
- **Рішення Власника:** Погоджено 3 основні рішення (Варіант B — окрема таблиця `chat_attachments`; 1536 px, JPEG 85%, очищення EXIF/GPS; реалізація 5 окремими PR №43–№47).
- **Вимоги до документу перед злиттям PR #42 (виконано у v1.2):**
  1. *Backup:* зафіксовано, що `backup_rules.xml` та `data_extraction_rules.xml` не копіюють `chat_photos`; передбачено плейсхолдер для відновленої текстової історії без фото; не обіцяти відновлення нерезервованих файлів.
  2. *Безпека ФС:* атомарний запис через `.tmp` файл та перейменування; обробка крашу процесу між записом на диск та вставкою в Room через Orphan Cleanup; повторна спроба очищення при невдалому `delete()`; валідація canonical path відносно базової папки; ізоляція підпапок рослин.
  3. *Конкурентність `withChatSending`:* м'ютекс НЕ утримується протягом мережевого запиту Gemini (лише короткочасний лок на лічильники та транзакції); зафіксовано поведінку при `clearChatHistory`, `deletePlant`, скасуванні корутини та Retry; додано перелік обов'язкових регресійних і crash-recovery тестів замість декларацій про «нульові ризики».
  4. *Квоти Gemini:* оцінку 1032 токени не вважати гарантованою; передбачено емпіричне вимірювання токенів через `countTokens` у тестах без платного тарифу та без змін у Firebase/Billing.
